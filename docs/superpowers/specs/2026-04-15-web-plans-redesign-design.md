# Web + Plans Redesign

**Status:** Design approved
**Scope:** `packages/contracts`, `packages/vendor-core`, `apps/api`, `apps/mcp`, `apps/web`
**Supersedes parts of:** `docs/superpowers/specs/2026-04-14-market-monorepo-design.md` (the `venues` / `shopping-list` / file-based-routing sections)

## 1. Goals

Build out the web app into a real catalog UI with four top-level sections — **Stores**, **Products**, **Vendors**, **Plans** — backed by a consistent, paginated, typed API. Replace the stateless shopping-list builder with server-side persisted **Plans** that carry user ids. Normalize every entity around an `id` + `slug` lookup model, rename `venues` → `stores` and `shopping-list` → `plan` end-to-end, and move the web router from file-based to config-based.

Success criteria:
- Every listing endpoint uses one consistent shape: `POST /v1/<resource>/query` with `{ skip, take, q, sort, ...filters }` body and `{ data, meta: { total, skip, take, sort? } }` response.
- Every entity has a globally unique `slug` alongside its UUID `id`; both resolve the same GET route.
- Plans are persisted, typed (`mixed` / `item-based` / `query-based`), and scoped to a `user_id` (with a real `users` table) so real auth can slot in later without API reshaping.
- Web app has working routes for stores, products, vendors, and plans, including a plan create dialog and a plan detail page with compute.
- MCP tools mirror the new HTTP surface 1:1.

## 2. API conventions

### 2.1 Listing convention

Listings are **POST** requests. The body carries pagination, search, sort, and entity-specific filters:

```ts
// Shared base, extended per entity
type PaginationBase = {
  skip?: number;  // default 0
  take?: number;  // default 50, max 500
  q?: string;     // free-text search (optional)
  sort?: { field: string; direction: 'asc' | 'desc' }[];
};
```

Each entity extends `PaginationBase` with a whitelisted `sort.field` picklist and flat filter fields (no nested `filters` bag). The path suffix is `/query`:

```
POST /v1/stores/query
POST /v1/catalog/items/query
POST /v1/plans/query
```

### 2.2 Response envelope

```ts
{
  data: T[],
  meta: {
    total: number,
    skip:  number,
    take:  number,
    sort?: { field: string; direction: 'asc' | 'desc' }[]  // echoed
  }
}
```

`hasMore` is derivable (`skip + take < total`) and intentionally omitted.

### 2.3 `idOrSlug` lookups

Every entity that has a detail route accepts a single path parameter `:idOrSlug`:

- If it parses as a UUID (v4), look up by `id`.
- Otherwise, look up by `slug`.

Both columns are globally unique, so resolution is unambiguous. Implemented in `apps/api/src/lib/id-or-slug.ts` with one resolver per resource (`resolveStoreIdOrSlug`, `resolveItemIdOrSlug`, `resolvePlanIdOrSlug`). Resolvers throw 404 when no row matches.

### 2.4 Slug generation

Slugs are globally unique and deterministically derived on upsert. Implemented in `@market/vendor-core`:

- `slugify(input)` — kebab-case, ascii-fold, strip non-alphanumeric, collapse dashes.
- `buildStoreSlug(vendor, vendorSlug)` → `${vendor}-${vendorSlug}`
  e.g. `wolt-carrefour-tbilisi-didube`
- `buildCategorySlug(storeSlug, vendorCategorySlug)` → `${storeSlug}-${vendorCategorySlug}`
- `buildItemSlug(storeSlug, itemName, vendorItemId)` → `${storeSlug}-${slugify(itemName)}-${shortHash(vendorItemId)}`
  where `shortHash` = first 6 chars of sha1(vendorItemId). Deterministic and stable across re-crawls.
- Plan slugs: `slugify(name)`, with a 6-char random suffix on unique-violation retry. Autogenerated at creation. **Stable** after creation — never regenerated on rename.

## 3. Route map

### 3.1 New state

```
Stores (renamed from venues)
  POST  /v1/stores/query                     body: { skip?, take?, q?, sort?, vendor?, productLine?, online? }
  GET   /v1/stores/:idOrSlug                  returns store + raw assortment content
  POST  /v1/stores/:idOrSlug/refresh-assortment   (admin, API_TOKEN)

Catalog
  POST  /v1/catalog/items/query              body: { skip?, take?, q?, sort?, mode?,
                                                     vendor?, storeIdOrSlug?, categoryIdOrSlug?,
                                                     minPriceMinor?, maxPriceMinor?, available? }
  GET   /v1/catalog/items/:idOrSlug           returns item detail
  GET   /v1/catalog/stats                     unchanged behavior; response renamed fields (venues → stores)

Plans (replaces shopping-list)
  POST  /v1/plans/query                      body: { skip?, take?, q?, sort?, type? }   (scoped to X-User-Id)
  POST  /v1/plans                            create: { name, type, strategy, vendor?, storeSlugs?, includeOffline? }
  GET   /v1/plans/:idOrSlug                   returns plan + lines (no compute)
  PATCH /v1/plans/:idOrSlug                   update metadata (name, strategy, vendor, storeSlugs, includeOffline); `type` is immutable
  DELETE /v1/plans/:idOrSlug
  POST  /v1/plans/:idOrSlug/lines            add a line (body is a `kind`-discriminated union)
  PATCH /v1/plans/:idOrSlug/lines/:lineId     update line (quantity, or query text on query lines)
  DELETE /v1/plans/:idOrSlug/lines/:lineId
  POST  /v1/plans/:idOrSlug/compute          recompute plan result using stored lines + plan metadata

Users
  POST  /v1/users                            create a user, body { name? }, returns UserSchema
  GET   /v1/users/me                         reads X-User-Id, returns user row or 404

Admin
  POST  /v1/admin/crawl                       unchanged
```

### 3.2 Removed

- `GET /v1/venues`
- `GET /v1/venues/:vendor/:slug`
- `POST /v1/venues/:vendor/:slug/refresh-assortment`
- `GET /v1/catalog/search`
- `POST /v1/shopping-list`

### 3.3 Auth surface

- `API_TOKEN` — unchanged. Still required on `/v1/admin/*` and `/v1/stores/:idOrSlug/refresh-assortment`.
- `X-User-Id` — new header carrying a UUID. Required on all `/v1/plans/*` routes via a `requireUser` preHandler; attached to `request.userId`. No DB validation per request — writes enforce the FK, reads just filter by it.
- Stores, catalog, users/create, users/me, and vendors (static, frontend-only) are open reads.

### 3.4 Behavior notes

- **Catalog items query** — when `q` is present, `mode` (`keyword` / `semantic` / `hybrid`) applies and default sort is `relevance`. When `q` is absent, `mode` is ignored and default sort is `name asc`.
- **Plan compute** is always explicit. `GET /v1/plans/:idOrSlug` returns plan + lines (cheap). `POST /v1/plans/:idOrSlug/compute` reads the stored lines, translates them into the existing builder input shape, runs the strategy logic, and returns a `ComputePlanResponse` (union of `CheapestPerItemPlan` / `SingleStorePlan`). `kind: 'item'` lines bypass the query-matching step entirely — their price + store are read directly from the items table.
- **Plan type is immutable** after creation. Changing type would invalidate existing lines; users copy a plan to convert it.

### 4.2 New tables

```ts
export const planType     = pgEnum('plan_type',      ['mixed', 'item-based', 'query-based']);
export const planStrategy = pgEnum('plan_strategy',  ['cheapest-per-item', 'single-store', 'both']);
export const planLineKind = pgEnum('plan_line_kind', ['query', 'item']);

users = pgTable('users', {
  id:        uuid('id').primaryKey().defaultRandom(),
  name:      text('name'),                        // optional label
  createdAt: timestamp('created_at', { withTimezone: true }).defaultNow().notNull(),
});

plans = pgTable('plans', {
  id:             uuid('id').primaryKey().defaultRandom(),
  slug:           text('slug').notNull(),
  userId:         uuid('user_id').notNull().references(() => users.id, { onDelete: 'cascade' }),
  name:           text('name').notNull(),
  type:           planType('type').notNull(),
  strategy:       planStrategy('strategy').notNull(),
  vendor:         vendorId('vendor'),             // optional filter constraint
  storeSlugs:     jsonb('store_slugs').$type<string[]>(),   // optional filter; stored as slugs (stable, human-readable)
  includeOffline: boolean('include_offline').notNull().default(false),
  createdAt:      timestamp('created_at', { withTimezone: true }).defaultNow().notNull(),
  updatedAt:      timestamp('updated_at', { withTimezone: true }).defaultNow().notNull(),
}, (t) => ({
  slugUq:     uniqueIndex('plans_slug_uq').on(t.slug),
  userIx:     index('plans_user_ix').on(t.userId),
  createdIx:  index('plans_created_ix').on(t.createdAt),
  nameTrgm:   index('plans_name_trgm').using('gin', sql`${t.name} gin_trgm_ops`),
}));

plan_lines = pgTable('plan_lines', {
  id:         uuid('id').primaryKey().defaultRandom(),
  planId:     uuid('plan_id').notNull().references(() => plans.id, { onDelete: 'cascade' }),
  position:   integer('position').notNull(),
  kind:       planLineKind('kind').notNull(),
  quantity:   integer('quantity').notNull().default(1),
  query:      text('query'),                       // populated when kind='query'
  itemId:     uuid('item_id').references(() => items.id, { onDelete: 'set null' }),  // populated when kind='item'
  createdAt:  timestamp('created_at', { withTimezone: true }).defaultNow().notNull(),
}, (t) => ({
  planPosIx:  index('plan_lines_plan_pos_ix').on(t.planId, t.position),
  // CHECK constraint (raw SQL in migration):
  //   kind='query' ⇒ query IS NOT NULL
  //   kind='item'  ⇒ item_id IS NOT NULL
}));
```

**Plan-type → line-kind enforcement** lives in the service layer (`services/plans.ts`). The DB alone can't express "if plan.type='query-based' then every plan_line.kind='query'" cleanly, and we'd rather fail fast in the service with a typed error anyway.

### 4.3 Migration order

`drizzle-kit generate` will emit a sequence; the steps below describe the intended order of diffs so the generator's output is easy to sanity-check:

1. **001** — create `users` table.
2. **002** — create `plan_type`, `plan_strategy`, `plan_line_kind` enums.
3. **003** — rename `venues` → `stores`; rename `venue_id` → `store_id` on `categories` + `items`; rename affected indexes.
4. **004** — add `slug` text columns (nullable) to `stores`, `items`, `categories`; backfill via SQL using the slug-builder logic; set NOT NULL; add unique indexes.
5. **005** — create `plans` and `plan_lines` tables with indexes and CHECK constraints; `plans.user_id` FK to `users.id`.

For a fresh dev DB the backfill in step 4 is a no-op.

export const SortDirectionSchema = v.picklist(['asc', 'desc'] as const);
export const SortItemSchema = <F extends readonly string[]>(fields: F) =>
  v.object({ field: v.picklist(fields), direction: SortDirectionSchema });

export const PaginationBaseSchema = v.object({
  skip: v.optional(v.pipe(v.number(), v.integer(), v.minValue(0)), 0),
  take: v.optional(v.pipe(v.number(), v.integer(), v.minValue(1), v.maxValue(500)), 50),
  q:    v.optional(v.pipe(v.string(), v.minLength(1))),
});

export function envelope<T extends v.BaseSchema<unknown, unknown, v.BaseIssue<unknown>>>(item: T) {
  return v.object({
    data: v.array(item),
    meta: v.object({
      total: v.pipe(v.number(), v.integer(), v.minValue(0)),
      skip:  v.pipe(v.number(), v.integer(), v.minValue(0)),
      take:  v.pipe(v.number(), v.integer(), v.minValue(1)),
      sort:  v.optional(v.array(v.object({
        field: v.string(),
        direction: SortDirectionSchema,
      }))),
    }),
  });
}

export const IdOrSlugParamsSchema = v.object({
  idOrSlug: v.pipe(v.string(), v.minLength(1)),
});

### 6.3 Compute translation

`services/plans.ts#compute(planIdOrSlug)`:

1. Resolve plan + lines from DB (filtered by `user_id`).
2. For each `plan_line`:
   - `kind = 'query'` → `{ query, quantity }` — passed to the existing query→candidates search path.
   - `kind = 'item'` → read the `items` row; construct an `ItemCandidate` directly (`venueSlug/storeSlug`, `itemId`, `priceMinor`, `currency`, `online`, `deliveryPriceInt` from the `stores` row). Short-circuit the match step entirely.
3. Feed the resulting unified line list plus plan metadata (`strategy`, `vendor`, `storeSlugs`, `includeOffline`) into the existing strategy implementations (`cheapest-per-item`, `single-store`), both of which are ported from the legacy `services/shoppingList.ts` without logic changes.
4. Return a `ComputePlanResponse` — `cheapestPerItem`, `singleStore`, or both depending on strategy.

### 6.4 Crawler slug population

Wherever the crawler upserts stores, categories, and items (currently inside `services/catalog.ts` or a crawler worker), the upsert calls `buildStoreSlug` / `buildCategorySlug` / `buildItemSlug` from `@market/vendor-core` and writes the result into the `slug` column. Because slugs are deterministic, re-crawls are idempotent.

### 8.3 URL-driven list state

Each list page declares a valibot `validateSearch` schema that covers `skip`, `take`, `q`, sort, and its entity-specific filters. The page reads via `Route.useSearch()`, builds a request body for the hook, and updates URL state via `navigate({ search: (s) => ({...}) })`. Bookmarking a list URL restores its filters exactly.

### 8.4 User boot sequence

`apps/web/src/api-client.ts` owns boot:

```
async function ensureUser(): Promise<string> {
  const existing = localStorage.getItem('market.userId');
  if (existing) return existing;
  const user = await fetch(`${base}${ROUTES.users.create}`, {
    method: 'POST',
    headers: { 'content-type': 'application/json', accept: 'application/json' },
    body: JSON.stringify({}),
  }).then((r) => r.json()) as User;
  localStorage.setItem('market.userId', user.id);
  return user.id;
}
```

`main.tsx` calls `ensureUser()` before `ReactDOM.createRoot(...).render(...)`. The plan-route hooks read the stored id and add `X-User-Id` to every request through the shared fetch wrapper.

### 8.5 Plan detail UX (`/plans/$idOrSlug`)

## 9. Auth (interim)

- **Header:** `X-User-Id: <uuid>`
- **Storage:** `localStorage['market.userId']`, set once at first app load via `POST /v1/users`
- **Tables:** real `users` table; `plans.user_id` FK enforces integrity on writes.
- **Enforcement:** `requireUser` preHandler on `/v1/plans/*` only. All read endpoints (stores, catalog, users/create) are open; admin endpoints still use `API_TOKEN`.
- **Explicit non-goals:** login/password/sessions, multi-device sync, security against impersonation. A real auth layer slots in later by replacing the header extraction with session/JWT extraction — the service layer and contracts do not change.
